동시성 처리를 넣었다고 해서 정말 맞게 동작하는지는 직접 부하를 걸어봐야 알 수 있습니다. 팔레트에서는 **사람이 몰려도 재고와 돈이 틀리지 않는지**, 그리고 **어디까지 버티는지**를 EC2 개발 서버에서 k6로 확인했습니다.

## 테스트 시나리오

1. 재고 100개인 상품에 300명이 동시에 주문
2. 같은 사용자가 주문 버튼을 연타
3. 5분 동안 연속으로 구매

## 확인 방법

- **요청**: k6로 시나리오별 요청을 보냈습니다
- **서버 상태**: Grafana로 CPU, Load, 스레드 수, GC 비율을 지켜봤습니다
- **정합성**: 응답 코드만 보지 않고, 테스트가 끝난 뒤 **DB에서 재고와 결제 내역을 직접 대조**했습니다. 팔린 수량과 남은 재고, 결제 건수가 서로 맞는지가 핵심이었습니다

## 결과

| 항목 | 결과 |
| --- | --- |
| 정합성 | 재고, 결제 오류 **0건** |
| 안정성 | 서버 에러 **0건** |
| 처리량 | 초당 **17건**까지 지연 없이 처리 |

## 병목 분석

처리량을 더 올리지 못한 이유를 Grafana 지표로 따라가 봤습니다.

[![부하 테스트 중 Grafana JVM 대시보드: CPU 사용률, Load, 스레드 수, GC 비율](/posts/palette-load-test-jvm.png)](/posts/palette-load-test-jvm.png)

그림을 누르면 크게 볼 수 있습니다.

- **서버 CPU**: 2코어 서버의 CPU가 99%까지 올랐고, Load는 17.6까지 치솟았습니다
- **스레드**: 대기 스레드가 270여 개까지 늘었습니다
- **JVM**: 정작 JVM 프로세스는 CPU를 최대 50%만 썼고, GC에 쓴 시간도 1.4%에 그쳤습니다

GC나 메모리 문제는 아니었습니다. 주문이 몰리면 요청들이 **재고 잠금을 기다리는 동안 DB 커넥션을 붙잡고 있어서** 커넥션 풀이 바닥났고, 커넥션을 얻지 못한 스레드가 쌓이면서 작은 서버의 CPU가 버티지 못했습니다.

주문 몰림 → 재고 잠금 대기 → 커넥션 풀 고갈 → 대기 스레드 270여 개 → 서버 CPU 99%

정리하면 병목은 **잠금 대기와 서버 CPU 부족**이었습니다.

## 같이 생긴 문제

부하 테스트 도중 분산 추적용 Tempo가 메모리 한계를 넘어 종료됐고, 재시작되는 동안 오류가 이어졌습니다. Tempo의 메모리 한계를 늘려 부하 상황에서도 추적이 끊기지 않게 했습니다.
