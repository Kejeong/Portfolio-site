주문하기 버튼을 두 번 누르거나, 응답이 늦어 앱이 같은 요청을 다시 보내면 **같은 주문이 여러 번** 들어옵니다. 팔레트는 주문을 만들 때 재고를 바로 차감하기 때문에, 그대로 두면 **재고가 여러 번 빠지고** 같은 주문이 여러 개 생깁니다. 같은 요청이 몇 번 와도 결과가 한 번 처리한 것과 같게 만드는 것, 이게 **멱등성**입니다.

## 같은 주문인지 어떻게 알아볼까

**Idempotency-Key**를 씁니다. 주문서 화면에서 키를 하나 만들고, 사용자가 다시 누르거나 앱이 재시도해도 **같은 키**를 헤더에 담아 보냅니다.

```http
POST /api/v1/orders
Idempotency-Key: 7f3c2a90-...      # 주문서 화면에서 만든 키 (1~64자)
```

서버는 같은 구매자가 같은 키로 보낸 주문이 이미 있으면 새로 만들지 않고 **처음 주문의 응답을 그대로** 돌려줍니다.

## 키로 조회만 하면 충분할까

"이 키로 만든 주문이 있나?" 조회만 하면 될 것 같지만, 두 요청이 **동시에** 들어오면 둘 다 "없음"을 보고 둘 다 주문을 만듭니다. 그래서 두 겹으로 막았습니다.

- **장바구니를 먼저 잠금**: 주문을 만들기 전에 구매자의 장바구니 행을 잠급니다. 같은 회원의 주문 요청은 한 번에 하나씩만 들어가고, 뒤에 온 요청은 앞의 주문이 저장된 뒤에 조회하므로 "이미 있음"을 보게 됩니다
- **(buyer_id, idempotency_key) 유니크 인덱스**: 그래도 빠져나가는 경우가 있다면 DB가 한 번 더 막습니다. 같은 구매자, 같은 키의 주문은 하나만 저장됩니다

## 같은 키 주문이 이미 있으면

| 상황 | 응답 |
| --- | --- |
| 같은 키 주문이 없음 | 새 주문 생성, 재고 차감 |
| 같은 키 주문이 있음 | 처음 주문을 그대로 반환 (재고는 다시 빼지 않음) |
| 같은 키 주문이 취소·만료됨 | 409, "새 키로 다시 주문해 주세요" |

취소되거나 만료된 주문의 키로 다시 요청하면, 예전 주문을 돌려주는 게 사용자가 원한 결과가 아닙니다. 그래서 409로 알리고 **새 키로 다시 주문**하게 했습니다. 키 형식이 잘못되면(비어 있거나 64자 초과) 400을 돌려줍니다.

## 결제에도 같은 원리

주문 서비스가 결제 서비스에 결제를 요청할 때도 **결제용 멱등 키**를 함께 보냅니다. 응답이 안 와서 같은 결제를 다시 요청해도 두 번 결제되지 않고 같은 결과를 받습니다. 이 내용은 [결과를 모르는 결제 글](/blog/payment-unknown-result)에 정리했습니다.

## 이벤트에도 같은 원리

서비스 사이의 Kafka 이벤트는 "최소 한 번" 전달이라 같은 이벤트가 두 번 올 수 있습니다. 받는 쪽은 이벤트 ID를 `processed_event`에 기록해 한 번만 처리합니다 ([Outbox·Kafka 글](/blog/transactional-outbox)).

## 정리

| 고민 | 선택 |
| --- | --- |
| 같은 주문인지 알아보기 | 주문서에서 만든 Idempotency-Key를 재시도에도 그대로 전송 |
| 조회만으로는 동시 요청을 못 막는다 | 장바구니 행을 먼저 잠금 |
| 그래도 빠져나가면? | (buyer_id, key) 유니크 인덱스로 DB가 한 번 더 막음 |
| 취소된 주문의 키로 재요청 | 409, 새 키 안내 |

결과적으로 같은 요청이 여러 번 와도 **주문은 하나만** 생기고 **재고도 한 번만** 차감됩니다.
