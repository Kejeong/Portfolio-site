팔레트는 처음에 주문, 재고, 결제를 **하나의 애플리케이션, 하나의 트랜잭션**으로 처리했습니다. 결제가 실패하면 주문도 함께 롤백되니 단순했습니다. 장애 격리와 도메인별 병렬 개발을 위해 주문(market)과 결제(payment)를 다른 서비스로 나누면서, 이 단순함이 사라졌습니다.

## 문제: 결제가 됐는지 알 수 없다

이제 주문 서비스는 결제 서비스를 **HTTP로 호출**합니다. 그런데 응답이 오지 않는 경우가 생깁니다.

- **시간 초과**: 결제 서비스가 처리는 했는데 응답이 늦게 와서 끊겼을 수 있습니다
- **5xx 오류**: 처리 도중 실패했는지, 처리 후 응답만 실패했는지 알 수 없습니다

예전처럼 롤백할 수도 없습니다. 원격 호출이라 이미 결제됐다면 **트랜잭션 롤백으로 되돌릴 수 없기** 때문입니다. 섣불리 주문을 취소하면, 실제로는 돈이 빠졌는데 주문이 사라질 수 있습니다.

## 해결: 4단계로 하나의 결과에 수렴시키기

PAYING 먼저 저장 → 같은 멱등 키로 결제 요청 → 응답이 없으면 그대로 두기 → 재확인 스케줄러가 정리

### 1. 결제 도중 서버가 죽으면? → PAYING으로 먼저 저장

결제를 요청하기 **전에** 주문을 `PAYING`(결제 중) 상태로 바꾸고 커밋합니다. 결제를 요청한 뒤 서버가 죽어도, `PAYING`으로 남은 주문을 나중에 다시 찾아 정리할 수 있습니다.

### 2. 다시 요청하면 두 번 결제되지 않을까? → 같은 멱등 키

결제 요청에는 주문마다 정해진 **결제 멱등 키**를 함께 보냅니다. 결제 서비스는 같은 키의 요청이 다시 오면 새로 결제하지 않고 **처음 결과를 그대로** 돌려줍니다. 같은 키로 처리 중인 요청이 또 들어오면 409로 막습니다.

### 3. 응답이 안 오면 결제가 된 걸까? → 알 수 없으니 그대로 둔다

| 응답 | 처리 |
| --- | --- |
| 2xx, 4xx (응답 받음) | 결과를 바로 주문에 반영 (결제 완료 또는 실패) |
| 시간 초과, 5xx (응답 없음) | 섣불리 취소하지 않고 `PAYING` 그대로 둠 |

모르는 상태에서 성공이나 실패로 단정하지 않는 것이 핵심입니다.

### 4. 그럼 결과는 언제 정해지지? → 재확인 스케줄러

재확인 스케줄러가 30초마다 돌면서, `PAYING`이 된 지 30초가 지난 주문을 **같은 멱등 키로 다시 결제 요청**합니다. 결제 서비스는 이미 처리한 결제라면 처음 결과를 돌려주고, 처리하지 않았다면 그때 처리합니다. 어느 쪽이든 **결과가 하나로 정해집니다.**

- **반영할 수 없으면 보상 취소**: 결제는 됐는데 그사이 주문을 반영할 수 없는 상태가 됐다면(예: 주문이 만료됨), 결제를 취소하는 **보상 처리**를 합니다
- **오래 안 풀리면 알림**: `PAYING`이 10분 넘게 정리되지 않으면 ERROR 로그를 남겨 Slack으로 알립니다
- **시간 설정의 순서**: 결제 요청의 응답 대기 시간(5초)은 재확인 시작 시간(30초)보다 짧게 둬서, 첫 요청이 아직 진행 중일 때 재확인이 끼어들지 않게 했습니다

## 왜 취소가 아니라 재확인인가

되돌릴 수 없는 원격 호출에서는 "모르면 취소"가 더 위험합니다. 이미 결제된 돈을 두고 주문만 취소하는 상황이 생기기 때문입니다. 그래서 **같은 키로 같은 결과를 다시 받아오는 쪽**을 선택했습니다. 멱등 키가 있기 때문에 몇 번을 다시 물어도 결제는 한 번만 일어납니다.

## 함께 읽으면 좋은 글

- 결제 결과가 정해지면 주문 상태 변경을 정산, 배송에 알려야 합니다. 이때 DB와 이벤트가 어긋나지 않게 한 방법은 [Outbox·Kafka 글](/blog/transactional-outbox)에 있습니다
- 같은 주문 요청이 여러 번 와도 하나만 만드는 방법은 [멱등성 글](/blog/order-idempotency)에 있습니다

## 정리

| 고민 | 선택 |
| --- | --- |
| 결제 도중 서버가 죽는다 | 결제 요청 전에 PAYING을 커밋 |
| 다시 요청하면 이중 결제 | 같은 멱등 키, 처리 중 중복은 409 |
| 응답이 없으면 결과를 모른다 | 단정하지 않고 PAYING 유지 |
| 결과는 언제 정하나 | 재확인 스케줄러가 같은 키로 다시 호출 |
| 결제됐는데 주문 반영이 불가능 | 보상 취소 |

결과적으로 **응답을 받지 못한 결제도 결국 하나의 결과로** 정리됩니다.
