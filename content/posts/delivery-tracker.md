팔레트는 배송이 끝나고 7일이 지나면 주문을 자동으로 구매 확정하고, 그때 정산이 시작됩니다. 그래서 **택배가 언제 도착했는지**를 사람이 일일이 입력하지 않고 자동으로 알아내야 했습니다. 배송 서비스(delivery-service)를 새로 만들면서 택배사 조회를 대신해 주는 **Delivery Tracker** API를 연동했습니다.

## Delivery Tracker는 어떤 API인가

- **GraphQL API**: 송장 조회(`track`)와 웹훅 등록(`registerTrackWebhook`)을 GraphQL 한 주소로 보냅니다
- **인증**: `Authorization: TRACKQL-API-KEY {clientId}:{clientSecret}` 헤더를 붙입니다
- **웹훅**: 송장을 등록해 두면 배송 상태가 바뀔 때 우리 서버로 콜백을 보내줍니다. 웹훅은 정해진 시간이 지나면 만료됩니다
- **할당량**: 초당 호출 수(기본 10회)와 동시에 걸어 둘 수 있는 웹훅 수(1,000개)에 한도가 있습니다

## 전체 흐름

송장 등록 → 웹훅 등록 → 상태 변경 콜백 → 확인 워커가 조회 → 배송 완료 반영

- **송장 등록**: 물류 담당자가 택배사와 송장 번호를 등록하면 배송이 `SHIPPED`가 됩니다
- **웹훅 등록**: 등록 직후 바로 부르지 않고, 60초마다 도는 스케줄러가 아직 웹훅이 없는 송장을 모아 등록합니다
- **콜백**: 배송 상태가 바뀌면 Delivery Tracker가 콜백을 보냅니다. 이때는 **"확인이 필요하다"는 표시만** 남깁니다
- **확인 워커**: 30초마다 표시가 있는 배송을 골라 `track`으로 직접 조회하고, 배송 완료면 `DELIVERED`로 바꾸고 `DeliveryCompletedEvent`를 발행합니다
- **주문 반영**: 주문 서비스가 이벤트를 받아 배송 완료를 기록하고, 7일 뒤 자동 구매 확정으로 이어집니다

## 설계하면서 고민한 것

### 콜백은 믿지 않고 신호로만 쓴다

콜백 본문에 담긴 상태로 바로 배송 완료를 처리하지 않았습니다. 콜백은 **"이 송장을 다시 확인해 보라"는 신호**로만 쓰고, 실제 상태는 확인 워커가 `track`으로 직접 조회해서 판단합니다. 그래서 콜백이 늦게 오거나, 순서가 뒤바뀌거나, 두 번 와도 결과가 달라지지 않습니다.

- **위조 막기**: 콜백 주소 끝에 32자 이상의 비밀 토큰을 붙였습니다. 토큰이 맞지 않으면 404로 응답하고, 로그에도 토큰을 남기지 않습니다
- **처리 실패**: 표시를 남기다 실패하면 503을 돌려줘서 Delivery Tracker가 다시 보내게 했습니다
- **표시 지우기**: 확인 워커는 조회를 시작한 시각 이전의 표시만 지웁니다. 조회하는 사이에 새로 온 콜백은 지워지지 않아 다음 실행에서 다시 확인합니다

### 외부 호출은 트랜잭션 밖에서

확인 워커는 짧게 읽기 → **트랜잭션 밖에서 외부 조회** → 쓰기 트랜잭션에서 잠그고 반영, 세 단계로 나눴습니다. 외부 API가 느려도 DB 커넥션과 잠금을 오래 붙잡지 않기 위해서입니다.

### 할당량을 넘지 않게

- **호출 제한기**: 스케줄러 여러 개가 같은 클라이언트를 쓰기 때문에, 모든 호출 합계가 **초당 5회**(기본 할당량의 절반)를 넘지 않도록 직접 만든 호출 제한기를 거치게 했습니다. "직전 호출 + 최소 간격"까지 기다리는 단순한 방식이라 별도 라이브러리가 필요 없습니다
- **나눠서 처리**: 스케줄러는 한 번에 50건씩 처리합니다. 초당 5회로 10초 안에 끝나는 양입니다
- **웹훅 수 한도**: 활성 웹훅이 900개(한도 1,000개)에 닿으면 새 등록을 미룹니다. 미뤄진 송장은 아래 안전망이 대신 확인합니다

### 웹훅이 만료되거나 빠져도 놓치지 않게

- **재등록**: 웹훅은 48시간 뒤 만료되므로, 만료까지 24시간보다 적게 남은 웹훅은 1시간마다 다시 등록합니다
- **안전망**: 웹훅을 놓쳤을 때를 대비해, 발송 후 2일이 지나도 `SHIPPED`인 배송은 매일 06:00에 한 번 더 조회합니다
- **사람이 볼 상태**: 배달 실패, 예외, 보관함 도착 같은 상태는 완료로 바꾸지 않고 경고 로그를 남겨 사람이 확인하게 했습니다

### 오류를 종류별로 나눈다

Delivery Tracker 응답을 인증 실패, 할당량 초과, 잘못된 요청, 서비스 장애로 나눠 각각 다른 예외로 던집니다. 잘못된 요청(없는 송장 등)은 다시 해도 소용없으니 표시를 지우고 넘어가고, 서비스 장애는 다음 실행에서 다시 시도합니다. 오류 메시지에서 인증 정보는 가렸습니다.

### HTTPS가 있어야 웹훅을 받을 수 있다

Delivery Tracker는 **https 주소로만 콜백을 보냅니다.** 그래서 웹훅이 켜져 있는데 콜백 주소가 `https://`가 아니면 서버가 아예 뜨지 않도록 막았습니다. 설정 실수를 배포 직후가 아니라 시작할 때 바로 알아채기 위해서입니다. 팔레트에 HTTPS를 붙인 과정은 [HTTPS 글](/blog/palette-https)에 정리했습니다.

## 관리자를 위한 길도 남겨 두기

자동 추적이 항상 성공하지는 않아서 관리자가 직접 처리할 수 있는 길도 만들었습니다.

- **수동 완료**: 관리자가 배송을 직접 완료 처리하면, 확인 워커와 똑같은 `DeliveryCompletedEvent`를 발행해 주문 쪽 흐름이 그대로 이어집니다
- **추적 실패 목록**: 송장을 등록하고 15일이 지나도 완료되지 않은 배송을 관리자 화면에 모아 보여주고, 택배사 조회 결과가 있었는지로 실패 원인을 나눠 보여줍니다

## 정리

| 고민 | 선택 |
| --- | --- |
| 콜백이 늦거나 중복되면? | 콜백은 신호로만, 상태는 직접 조회 |
| 외부 API가 느리면? | 조회는 트랜잭션 밖, 반영만 짧은 트랜잭션 |
| 할당량을 넘으면? | 초당 5회 호출 제한, 50건씩 처리, 웹훅 900개 한도 |
| 웹훅이 빠지면? | 만료 전 재등록, 발송 2일 뒤 매일 안전망 조회 |
| 자동으로 안 되면? | 관리자 수동 완료, 15일 추적 실패 목록 |
