팔레트의 주문은 생성하면 재고를 먼저 잡아 두고, **15분 안에 결제하지 않으면 만료**되어 재고를 되돌립니다. 만료는 스케줄러가 처리합니다. 그런데 만료 직전에 결제가 들어오면, 결제 요청과 만료 스케줄러가 **같은 주문을 동시에** 건드리게 됩니다.

## 문제: 결제됐는데 만료될 수 있다

```text
결제 요청                        만료 스케줄러
주문 상태 확인: 결제 대기         주문 상태 확인: 결제 대기 (만료 시각 지남)
결제 반영 → 결제 완료             만료 처리 → 재고 복원, 주문 만료
```

둘 다 "결제 대기"를 보고 각자 처리하면, **돈은 빠졌는데 주문은 만료**되고 재고도 되돌아가는 일이 생깁니다. 결제, 취소, 만료 중 **반드시 하나만** 반영돼야 합니다.

## 고민: 낙관적 락으로는 안 될까

낙관적 락(버전 비교)은 일단 둘 다 진행시키고, 저장할 때 늦은 쪽을 실패시킵니다. 충돌이 드물 때 좋은 방법입니다. 하지만 이 상황은 달랐습니다.

- **둘 중 하나는 반드시 실패해야 한다**: 충돌이 "가끔"이 아니라, 겹치면 무조건 한쪽을 막아야 하는 상황입니다
- **실패 뒤 처리가 복잡하다**: 결제 쪽이 늦게 실패하면 이미 진행한 결제를 되돌리는 처리가 따로 필요합니다

그래서 처음부터 한쪽이 기다리게 하는 **비관적 락**을 골랐습니다.

## 해결: 잠그고, 다시 확인하고, 여유를 둔다

주문 행 잠금 → 잠근 뒤 상태 재확인 → 먼저 바꾼 쪽만 반영

- **주문 행을 먼저 잠금**: 결제, 취소, 만료 모두 주문을 `SELECT ... FOR UPDATE`로 잠근 뒤 처리합니다. 동시에 들어와도 한쪽만 먼저 들어갑니다
- **잠근 뒤 상태를 다시 확인**: 잠금을 기다렸다 들어온 쪽은 그사이 상태가 바뀌었을 수 있습니다. 잠근 뒤 다시 보고, 결제 대기면 반영하고, 이미 결제됐으면 만료를 건너뜁니다
- **스케줄러에 유예 시간**: 만료 스케줄러는 만료 시각이 지나고 **1분을 더 기다린 뒤** 처리합니다. 만료 직전에 들어와 처리 중인 결제가 먼저 끝날 수 있게 여유를 둔 것입니다

| 잠근 뒤 본 상태 | 결제 요청 | 만료 스케줄러 |
| --- | --- | --- |
| 결제 대기 | 결제 반영 | 만료 처리 |
| 이미 결제됨 | (같은 요청이면 같은 결과) | 건너뜀 |
| 이미 만료·취소됨 | 결제하지 않음 | 건너뜀 |

## 스케줄러는 한 건씩

만료 스케줄러는 대상을 id 커서로 나눠 **한 건씩 각자 트랜잭션**으로 처리합니다. 여러 주문을 한 트랜잭션으로 오래 잠그지 않고, 한 건이 실패해도 나머지는 계속 처리됩니다. 상품과 주문을 함께 잠글 때는 교착이 생기지 않게 **상품 → 주문** 순서를 지킵니다 ([교착 방지 글](/blog/lock-ordering-deadlock)).

## 정리

| 고민 | 선택 |
| --- | --- |
| 결제와 만료가 동시에 들어온다 | 주문 행을 FOR UPDATE로 잠금 |
| 낙관적 락 vs 비관적 락 | 둘 중 하나는 반드시 실패해야 해서 비관적 락 |
| 잠금을 기다린 사이 상태가 바뀐다 | 잠근 뒤 상태를 다시 확인 |
| 만료 직전 결제 | 스케줄러에 1분 유예 |
| 스케줄러가 오래 잠근다 | id 커서와 건 단위 트랜잭션 |

결과적으로 결제, 취소, 만료가 겹쳐도 **먼저 상태를 바꾼 처리 하나만** 반영됩니다.
