팔레트는 서비스 7개와 Gateway로 나눈 MSA 프로젝트입니다. 서비스는 많아졌는데 서버는 두 대뿐이어서, **어느 서버와 어느 서비스에 여유가 없는지**를 바로 볼 수 있어야 했습니다. 오류가 나면 서버에 들어가 로그를 뒤지는 대신 **바로 알림을 받는 것**도 목표였습니다.

## 주어진 조건

- **앱 서버 (EC2-A)**: t3.large, 메모리 8GB. Gateway와 서비스 6개, AI 서비스(k3s), 모니터링
- **데이터 서버 (EC2-B)**: t3.medium, 메모리 4GB. PostgreSQL, Kafka, Elasticsearch
- **목표**: 서버를 늘리지 않고 **주어진 용량 안에서** 앱 8개와 DB, Kafka, 모니터링까지 모두 올리기

## 메모리를 아끼는 설정

- **JVM**: 서비스마다 컨테이너 메모리 한도를 정하고(1GB, 가벼운 서비스는 768MB), 힙은 그 한도의 75% 안에서 잡도록 맞췄습니다
- **Kafka, Elasticsearch**: 힙을 고정해서 메모리를 예상한 만큼만 쓰게 했습니다
- **로그와 지표 보관**: 보관 기간과 용량에 상한을 뒀습니다. Loki는 14일, Prometheus는 7일입니다

## 서버 대시보드

Prometheus로 지표를 모으고 Grafana에서 앱 서버와 데이터 서버를 나눠 봤습니다. 서버의 남은 메모리, 디스크, CPU와 함께 **서비스별 JVM 힙 사용량**을 한 화면에 두어서, 부하가 걸렸을 때 어느 서버와 서비스에 여유가 없는지 바로 알 수 있게 했습니다.

[![Grafana 서버 대시보드: 앱과 데이터 서버의 남은 메모리, 디스크, CPU, 서비스별 JVM 힙](/posts/palette-server-dashboard.png)](/posts/palette-server-dashboard.png)

캡처한 시점에는 앱 서버에 메모리가 약 2GB, 데이터 서버에 약 1GB 남아 있었고, 서비스 중에서는 market의 힙 사용량이 가장 컸습니다(최대 230MiB).

## 로그 모니터링과 ERROR 알림

처음에는 로그가 컨테이너 표준 출력에만 남아서, 오류가 나면 서버에 들어가 직접 찾아봐야 했습니다. 팀에서 함께 서버 한 대(디스크 50GB)에 맞춰 로그 위주로 가볍게 구성했습니다.

Spring Boot JSON 로그 → Alloy 수집 → Loki 14일 보관 → Grafana 1분마다 집계 → Slack ERROR 알림

ERROR가 생기면 Slack으로 바로 알림이 와서 **팀원 모두가 함께 확인**했습니다.

## Slack으로 이어 붙인 팀 자동화

리뷰 요청과 오류 확인을 사람이 매번 챙기지 않아도 되도록, 팀에서 쓸 스킬을 직접 만들어 흐름에 붙였습니다.

- **ERROR 알림 봇**: 서비스별 ERROR 로그를 원인, 발생 위치, 배포 버전, 확인할 것까지 메시지 하나로 보내줍니다. 서버 로그를 뒤지지 않고 채널에서 바로 확인하고 대응했습니다
- **PR 자동 공유 스킬**: PR을 올리면 PR 링크와 작업 내용을 정리해 채널에 올리고, 관련 담당자를 @멘션해 리뷰어로 지정합니다. 리뷰 전에는 Claude 코드리뷰 스킬로 한 번 더 점검했습니다

## 분산 추적으로 느린 구간 찾기

서비스가 나뉘면 느린 API가 **어느 서비스 구간에서 늦어지는지** 알기 어렵습니다. 서비스 사이의 요청 흐름을 Tempo로 추적하고, Prometheus 메트릭과 함께 Grafana에서 보면서 분석했습니다.

부하 테스트 도중에는 메모리 한계를 낮게 잡아 둔 Tempo가 버티지 못하고 종료됐고, 재시작되는 동안 오류가 이어졌습니다. **Tempo의 메모리 한계를 늘려** 부하 상황에서도 추적이 끊기지 않게 했습니다.
