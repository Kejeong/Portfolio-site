## 설계 기준

- 현장마다 50~100명이 쓰는 **단순한 흐름**
- 협력사가 제출하고 **원청이 승인**하는 구조
- **관리자 개입 최소화**
- 장비 번호는 **법규 기준**에 맞게

## 점검 워크플로 설계

점검 → 지시 → 배분 → 조치 → 현장 승인 → 본사 승인의 6단계로 흐르고, 반려되면 승인반려 상태로 돌아가 다시 조치합니다.

| 단계 | 점검 | 지시 | 배분 | 조치 | 현장 승인 | 본사 승인 |
| --- | --- | --- | --- | --- | --- | --- |
| 상태 | 확인필요 | | 조치필요 | 조치완료 | | 승인완료 |

### 흐름과 상태

- **상태 정의**: 점검부터 현장, 본사 승인까지의 흐름을 분석해 점검 상태를 확인필요부터 승인완료까지 7단계로 정의했습니다
- **판단 기준**: 조치 단계의 상태는 부적합 항목, 발행, 조치 건수를 집계해 서버에서 정하도록 설계해서 웹과 모바일이 같은 기준으로 판단하게 했습니다
- **조치 추적**: 부적합 항목은 추가위험발굴이나 부적합보고서로 발행해 조치자에게 지시 알림을 보내고 첨부 파일도 함께 맞춰서, 점검부터 조치까지 한 흐름으로 추적할 수 있게 했습니다
- **결재 연동**: 승인 단계는 공통 결재와 연동해 결재 상태(상신, 진행, 반려, 완료)를 점검 상태로 바꾸고, 점검을 등록할 때 기본 승인라인을 자동으로 만들어 현장, 본사 2단계 승인이 결재 흐름과 맞도록 했습니다

### 수정하거나 반려될 때

- **정합성**: 발행 문서를 저장하거나 삭제할 때마다 상태를 다시 계산하고, 반려 후 재점검은 승인반려로 되돌려서 어떤 경로로 수정해도 상태와 데이터가 어긋나지 않게 했습니다
- **문서 회수**: 점검 결과가 바뀌면 이미 발행된 추가위험발굴과 부적합보고서를 회수해서, 조치나 결재 같은 다른 메뉴의 데이터와도 어긋나지 않게 처리했습니다

## 장비 안전점검 설계

- **결재선**: 협력사가 제출하고 원청이 승인하는 관계를 결재 흐름에 반영했고, 고객사 요청에 따라 제출자가 승인자를 직접 지정할 수 있게 바꿔 관리자가 개입하지 않아도 제출부터 승인까지 진행되도록 했습니다
- **장비 번호**: 건설기계 등록번호는 개정 전과 후 두 형식을 정규식으로 검증해 구분 코드(NEW/OLD)와 함께 저장했고, 같은 현장에서는 중복 등록을 막고 다른 현장에 이미 있는 장비는 정보를 불러와 다시 쓰게 해서 법규 형식에 맞지 않거나 중복된 장비가 등록되지 않도록 했습니다
- **점검항목**: 장비 유형을 고르면 기본 점검항목이 자동으로 만들어지게 해서 현장의 입력 부담을 줄이고 점검 기준을 통일했습니다

## 운영 중 오류 대응

사용자 오류 접수 → ELK 로그 확인 → 개발 환경에서 재현 → 원인 추적, 수정 → 배포

- **운영 대응**: 실제 운영 중인 서비스라 사용자 오류가 들어오면 ELK로 로그를 확인하고, 개발 환경에서 같은 상황을 재현해 테스트하면서 원인을 찾은 뒤 수정해서 배포까지 마무리했습니다
- **오류 추적**: 모바일에서도 처리하는 흐름이라 오류가 나면 어느 단계에서 멈췄는지 알 수 있도록 상태 컬럼을 추가해, 오류가 난 시점과 원인을 추적할 수 있게 했습니다
- **레거시 유지보수**: Java 7 기반의 오래된 협력업체 시스템에서 오류가 날 때마다 원인을 찾아 고쳤고, 리포트가 출력되지 않았을 때는 디스크가 가득 찬 것이 원인이어서 쌓여 있던 as-is 폴더를 정리해 복구했습니다
