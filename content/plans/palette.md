## 1. 프로젝트 개요

**팔레트**는 인플루언서가 추천한 뷰티, 의류 상품을 1인 쇼핑몰 및 브랜드 셀러가 입점해 판매하는 **입점형 이커머스 플랫폼**이다. 플랫폼은 중개·결제·정산을 맡고, PG(토스페이먼츠·헥토) 연동 예치금과 월 정산(수수료 10%)으로 안전한 거래 환경을 제공한다.

- **API 명세서**: [palette-shop.duckdns.org/swagger-ui](https://palette-shop.duckdns.org/swagger-ui/)
- **Git 저장소 (BE)**: [prgrms-be-adv-devcourse/beadv8_2_TRSS_BE](https://github.com/prgrms-be-adv-devcourse/beadv8_2_TRSS_BE)
- **Git 저장소 (FE)**: [prgrms-be-adv-devcourse/beadv8_2_TRSS_FE](https://github.com/prgrms-be-adv-devcourse/beadv8_2_TRSS_FE)

## 2. 프로젝트 목표

- **MSA 전환**: 모놀리스를 서비스 7개 + Gateway로 나누고, 서비스마다 DB 스키마를 분리한다.
- **데이터 정합성**: Outbox + Kafka, 멱등 키, 보상 처리로 서비스 경계를 넘는 흐름을 안전하게 만든다.
- **안전한 돈 흐름**: 예치금·홀딩·정산 지급을 모두 원장에 남기고, PG 장애 시 결과를 다시 확인해 확정한다.
- **AI 개인화**: 피부·성분 설문 기반 뷰티 추천과 FAQ 챗봇을 제공한다.
- **운영 가능한 배포**: 자동 배포, k3s 오토스케일링(AI), 모니터링과 Slack 알림을 갖춘다.

## 5. AI 추천 기능

| 구분 | 행동 기반 추천 (market) | 뷰티 맞춤 추천 (ai) |
| --- | --- | --- |
| 신호 | 구매, 리뷰, 찜, 장바구니, 최근 본 상품 | 뷰티 설문(피부 타입·고민·성분), 상품 전성분 |
| 기법 | Elasticsearch 유사 문서 검색 | OpenAI 임베딩 + pgvector 유사도 + 성분 필터 |
| 제공 | 회원님을 위한 추천, 비슷한 상품 | 맞춤 상품 추천, 크리에이터 추천 |

- **맞춤 상품 추천**: 피하는 성분이 든 상품은 반드시 빼고, 피부 프로필과 비슷한 순서로 추천 이유와 함께 보여 준다.
- **크리에이터 추천**: 나와 피부 고민이 비슷한 인플루언서를 추천한다.
- **FAQ 챗봇**: 등록된 FAQ를 근거로 답한다(RAG, gpt-4o-mini). 회원당 1분 10회로 제한한다.

## 7. MSA 분리 지점

| 서비스 | 담당 |
| --- | --- |
| gateway | 라우팅, JWT 검증 |
| member | 회원, 판매자, 인플루언서 |
| market | 상품, 주문·반품, 쿠폰, 리뷰 |
| payment | 지갑, 충전, 결제, 환불, 정산 지급 이체 |
| settlement | 정산 후보, 월 정산 배치 |
| delivery | 배송, 송장, 배송 추적 |
| notification | 알림, SSE |
| ai | 뷰티 추천, FAQ 챗봇 |

### 분리 기준

- **스키마 소유**: 각 서비스는 자기 스키마만 쓰고, 서비스 사이에는 FK를 두지 않는다.
- **트랜잭션 경계**: 한 트랜잭션이어야 하는 상품과 주문(재고 차감 + 주문 생성)은 market에 함께 둔다.
- **책임 분리**: 상태 변경과 돈 이동을 나눈다. 반품은 market, 환불은 payment가 맡는다.

## 8. 서비스 간 통신 흐름

| 방식 | 언제 | 예시 |
| --- | --- | --- |
| 동기 HTTP (내부 API) | 결과가 바로 필요한 명령·조회 | 주문 → 결제, 정산 → 지급 이체, 회원·판매자 확인 |
| Kafka (Outbox) | 알리기만 하면 되는 후속 처리 | 결제 완료 → 배송 생성·알림, 구매 확정 → 정산, 반품 승인 → 환불 |

- 요청 경로: 사용자 → Nginx → Gateway(JWT 검증) → 각 서비스
- 내부 API는 `X-Internal-Key`로 인증하고, 외부에서는 호출할 수 없다.
- 이벤트는 Outbox에 먼저 저장한 뒤 발행하고, 받는 쪽은 중복을 걸러 한 번만 처리한다.

### 대표 흐름: 주문 → 정산

1. market: 주문 생성(재고 차감 + 쿠폰 예약) → payment 내부 API로 결제
2. 결제 완료 이벤트 → delivery가 배송 생성, notification이 알림 전송
3. 배송 완료 이벤트 → market이 기록하고 7일 뒤 자동 구매 확정
4. 구매 확정 이벤트 → settlement가 정산 후보 생성 → 매월 10일 payment로 지급

## 9. 결제 도메인 분리의 데이터 흐름 변경점

| 항목 | 변경 전 (모놀리스) | 변경 후 (payment-service) |
| --- | --- | --- |
| 주문 → 결제 | 같은 트랜잭션 안에서 직접 호출 | 내부 HTTP 호출 + 멱등 키 |
| 실패 처리 | 전체 롤백 | 결제는 됐는데 주문 반영이 실패하면 보상 취소 |
| 결과 불명 | 생기지 않음 | 결제 중(PAYING)으로 두고 같은 멱등 키로 재확인 |
| 지갑 생성 | 가입 트랜잭션 안에서 생성 | 가입 이벤트를 받아 생성 |
| 반품 환불 | 없음 | 반품 승인 이벤트를 받아 환불 |
| 정산 지급 | 정산 트랜잭션 안에서 이체 | 내부 HTTP 호출 + 멱등 키 |

### 돈의 이동

- **결제**: 구매자 지갑 → 홀딩(상품 금액), 플랫폼 지갑(배송비)
- **반품**: 홀딩 → 구매자 지갑
- **정산**: 홀딩 → 판매자 지갑(90%), 플랫폼 지갑(수수료 10%)
